# Mapsift decision log

> **What this is.** A grep-able derived index of foundation versions and closed decisions. It is **not a source
> of truth.** The foundation's section 15 changelog is the authority for version history, and the document named
> in each line is the authority for that decision; this file only mirrors them in flat, greppable lines so a
> version or a decision can be found without reading a full changelog. If this file and the foundation disagree,
> the foundation wins and this file is the one to fix.
>
> **Format.** One line per entry: `## [YYYY-MM-DD] <type> | <one-line description>`, where `<type>` is
> `version` (a foundation version bump, mirrored from section 15) or `decision` (a decision closed in a derived
> document that did not bump the foundation). Grep `version` for the release history, `decision` for closed
> calls that are not in the changelog.

## [2026-07-31] version | v0.14 — the ratified database major moves from PostgreSQL 16 to 18. The request was to pin "the LTS version" and the premise is false: PostgreSQL designates no long-term-support version, supporting every major for five years from initial release, shipping a major yearly and a minor quarterly, and recommending you always run the current minor. ## [2026-07-31] version | v0.15 — performance is engineered, and the established technique is researched before an implementation is settled for, on the same discipline the external-dependency rule applies to versions. Two classes treated differently: structural performance is free at design time and therefore not optional (the index the query needs, the batch that replaces a loop of round trips, the critical section held for one statement instead of one transaction, the payload that crosses a boundary once), and skipping one is a defect with a performance symptom; complexity-adding optimisation is bought with a measurement and never a hunch, generalising the tiling gate of section 6. ## [2026-07-31] decision | ADR-0004 accepted: the sync ordering strategy is the per-project version, allocated inside the flush transaction so version order is commit order by construction. Chosen on FAILURE MODE rather than throughput: its contention is local, proportional and diagnosable, while the transaction-id watermark fails non-locally twice (any unrelated writing transaction stops the feed for every user, measured at a full 4 s stall; and its cursor is bound to the physical identity of the cluster, so a logical restore silently invalidates every offline client's cursor, which matters because Mapsift's cursor lives on field devices for weeks). Row-versioning with a client view record was eliminated on read cost (2,615 rows scanned per poll at a 5,000 backlog, halving write throughput). Delivers the SP-1 exit — `specs/adr/0004-sync-ordering-strategy.md`.
## [2026-07-31] decision | Two engineering rules are part of the ADR-0004 decision rather than optimisations to add later, because serialisation is caused by how long the lock is held rather than by the number of writers: allocate the whole version range in ONE statement per flush, and take the allocation LAST, so validation, dedup, contiguity, feature versions and the conflict rule all run outside the critical section. Measured with ten people editing while a client flushes 3,000 operations: worst interactive save falls from 782 ms to 40 ms and the flush itself gets four times faster. LATE matters more as pushes get heavier, since the critical section stops growing with them.

## [2026-08-04] decision | **ADR-0005 closes the tenant-isolation mechanism (MAP-1, agenda item 1): row-level security, enabled AND forced, with per-tenant views rejected.** Views lose on three counts: they need DDL for every new tenant, which turns creating a personal account into a schema migration and contradicts PRD M1; they protect reads and protect writes only with `WITH CHECK OPTION`; and the single parameterised view that avoids per-tenant DDL is row-level security with the guarantees removed, because any role with privileges on the underlying table reads straight past it. ## [2026-08-04] trap | **The empty-string trap, and it is the one nobody expects.** A transaction-scoped `set_config` does not revert to *unset* when the transaction ends; it reverts to the session value, which for a never-set custom parameter is the **empty string**, and `''::uuid` throws. So the obvious policy `tenant_id = current_setting('mapsift.tenant_id', true)::uuid` works on the first transaction of a connection and raises `invalid input syntax for type uuid: ""` on every one after it, which appears **only on a pooled or persistent connection** and reads like a broken database rather than a broken policy. The fix is `nullif(current_setting('mapsift.tenant_id', true), '')::uuid`. Measured against PostgreSQL 18.4 on 2026-08-04.
## [2026-08-04] finding | **The leak has a shape and it is the session-scoped binding.** Measured: `set_config(..., false)` survives into a later transaction on the same connection, so with `CONN_MAX_AGE` or the psycopg pool it reaches the **next request**, which may belong to another tenant. psycopg hands a connection to the next client in idle state without clearing session state (cleanup is the application's `reset` callback), and Django's own manual says the same in reverse: restore the parameter, force it per request, or stop reusing connections. Hence the rule: the binding is **transaction-scoped, always**, and a session-scoped one is prohibited by name.
## [2026-08-04] finding | **The tenant parameter is a binding, not a capability, and the limit is irreducible.** Measured: an unprivileged role sets the parameter to any value it likes, `REVOKE SET ON PARAMETER` changes nothing, and `pg_parameter_acl` holds no entry, because a custom two-part parameter is a placeholder the server accepts from anyone. So row-level security stops a **query** from crossing the wall and does not stop **code that can run arbitrary SQL on an already-bound connection**. That is the honest edge of what the wall buys, and it is why the parameterised binding statement is a security control here rather than a style preference.
## [2026-08-04] trap | **Referential integrity is a documented hole in the wall, and it was measured open.** PostgreSQL states that referential integrity checks always bypass row security. In practice: a row bound to tenant A **successfully created a foreign key to a row of tenant B**, and a primary-key collision against an invisible row of another tenant reported itself as a unique violation. A **composite key over `(tenant_id, id)` closes the first completely** (re-measured: cross-tenant reference now fails, same-tenant succeeds), at one unique index per table, and every **natural** unique key is unique per tenant rather than globally.
## [2026-08-04] finding | **FORCE is what makes the wall true in the test suite, not only in production.** Measured: the table owner with row-level security enabled and not forced sees every tenant (3 of 3), and so does a `SECURITY DEFINER` function owned by it; `FORCE ROW LEVEL SECURITY` closes both at once (2 and 2). Migrations and the Django test database are created by the owning role, so **without FORCE the entire suite would run outside the wall it exists to prove**. A `BYPASSRLS` role still sees everything after FORCE, which is why no role in this system is granted it.

## [2026-08-04] decision | **ADR-0006 closes the identifier variant (MAP-2, agenda item 2): a random 128-bit identifier, not a time-ordered one.** Four reasons in weight order: the locality a time-ordered identifier buys is contingent on a clock this model distrusts by construction (I10); M3 requires opacity and a time-ordered identifier publishes its creation instant; N9 puts the operation identifier in every log line on the sync path, so that instant would travel everywhere, and N5 separates a parcel vertex (the subject matter) from a person's sequence of capture instants (their whereabouts); and ADR-0004 already owns ordering through the per-project and per-feature versions, so the identifier does not need a second job.
## [2026-08-04] finding | **The measurement inverted the expected trade, which is why it was run.** PostgreSQL 18.4, 500,000 rows per arm inserted as 500 batches of 1,000: perfectly ordered gave a 15 MB index at 89.98% leaf density; random gave 19 MB at 71.87%; and **time-ordered with one row in five minted on a clock up to thirty days out gave 37 MB at 52.86% density**, which is 2.45 times the well-behaved ordered index and roughly twice the random one. Skewed keys do the worst of both, splitting pages in a band that is also being appended to and leaving the halves behind. So the choice was never ordered against random, it was ordered-if-every-clock-is-right against random-always.
## [2026-08-04] finding | **Two honesty notes recorded with those numbers, because a measurement without its conditions is decoration.** The whole dataset fit inside the container's 128 MB `shared_buffers`, which is the regime where random keys are **cheapest**, so the insert-time column understates the random penalty at a scale where the index exceeds memory; the size and density columns are structural and do not. And the skew arm is a model rather than a census: one row in five and thirty days are a plausible field population, so the direction of the result is robust and the exact multiple is not.
