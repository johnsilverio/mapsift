# Mapsift Data and Tooling References

> **Purpose.** A stable reference catalog for two things the team needs while building and testing Mapsift: where to get real and test geospatial data across the formats, coordinate systems, geometry types, and sizes that matter, and where the canonical documentation for each analysis tool lives so the use case and the expected behavior are known before a developer tests it. This is a reference document, not a test plan; the test plan is a separate document that points here.
>
> **How a developer uses this.** Before testing a feature, you need to know two levels of "works." Level one is "the tool ran without error and returned a geometry," a smoke test you and the other developer run without the domain engineer. Level two is "the tool returned the correct result for its use case," which needs the use case and the expected behavior, both linked below per tool. Level three, "this result matches the reality of the biome," is the engineer's domain validation and is out of scope here. This catalog arms levels one and two.
>
> **Verified.** Links and facts checked against the live sources in **June 2026**, except where an entry carries its own later date. Geospatial portals move things; if a deep link rotates, the portal root and the dataset name are given so it can be found again.
>
> **Date discipline, and where this document is weaker than `specs/dependencies.md`.** Entries that read "mid-2026" carry that June check and nothing more precise. The volatile ones are named here so nobody quotes them as current without re-checking: **object-storage egress pricing**, the **CDSE quotas and processing-unit limits** (section 1.5), the **MapBiomas collection number**, and the **GADM version**. Under the rule `specs/dependencies.md` sets, a claim with no verification date is a claim to distrust, and that rule applies to this document too.
>
> **A reference document does not decide.** Blocks labelled *Microdecision* and *Decision shape* below are **evidence and reasoning offered to a decision**, never the decision. Where one touches an open question, the owner named in the foundation decides and this catalog only supplies the input; where one touches an architectural gate, the gate's condition governs. Section 2.1 already states the correct posture ("PRD M5 is the authority, not this paragraph") and it applies throughout.

## Part 1. Data sources for a robust test corpus

### 1.1 The test matrix (variety beats volume)

The import path breaks on the awkward cases, not on the pretty GeoJSON. Build the fixture corpus to cover four axes deliberately, because each one is where GDAL or the SIRGAS2000 reprojection earns its keep:

- **Format:** Shapefile (zipped, and one with a part missing to test the validation error), GeoPackage, GeoParquet, FlatGeobuf, GeoJSON, KML, KMZ, GPX, GeoTIFF, COG, CSV with coordinates.
- **Coordinate reference system:** WGS84 (EPSG:4326); SIRGAS2000 geographic (EPSG:4674) and SIRGAS2000 UTM in more than one zone (Brazil spans several UTM zones, so the reprojection must land all of them, and the Brazilian sources in 1.2 arrive natively in these); plus at least one foreign national grid (European ETRS89 / LAEA EPSG:3035, US State Plane), since a general-purpose tool reprojects every national grid, not only Brazil's (the sources in 1.4 cover these).
- **Geometry type:** point, line, polygon, multipolygon, and a polygon with a hole (to exercise complex geometry per anti-requirement AR4).
- **Size:** a small hand-drawable layer, a mid-size vector (tens of thousands of features) to test the layer-versus-element threshold, and a heavy raster to test the tile path and the I6 memory budget.

### 1.2 Brazilian domain sources (the anchor, and where SIRGAS2000/UTM is real)

- **MapBiomas (land cover and use).** The canonical Brazilian wall-to-wall annual land-cover-and-use product, Landsat-based via Google Earth Engine, and as of mid-2026 the live edition is **Collection 10.1**, covering 1985 to 2024 at 30 m, an incremental refresh of the Collection 10 line launched in August 2025, with the per-biome and per-municipality area statistics refreshed in February 2026. It is not a single raster but a family of thematic products on independent collection numbers and cadences: core land cover and use, land-use transitions, deforestation and secondary vegetation, and the dedicated Fire, Water, Agriculture (irrigation and cropping cycles), Mining (industrial versus garimpo), Pasture vigor, Urban, and Soil sub-products, which is what makes it direct material for change detection rather than a single snapshot. A 10 m Sentinel-2 collection exists but is still **beta** (roughly 2016 to 2023), so the 10 m line is not yet at production parity with the 30 m one. The data is **GeoTIFF** (categorical pixel equals class code), native CRS **WGS84 (EPSG:4326)**, license **CC-BY-SA 4.0** (attribution plus share-alike, which propagates to any derived layer Mapsift redistributes). Access is the [MapBiomas platform and Toolkit](https://plataforma.brasil.mapbiomas.org/), the [downloads page](https://brasil.mapbiomas.org/en/downloads/), Google Earth Engine assets under the public `projects/mapbiomas-public` project, and direct per-year GeoTIFFs from Google Cloud Storage under `storage.googleapis.com/mapbiomas-public/...` (the platform download and toolkit pages give the exact per-year paths). **Microdecision:** MapBiomas 30 m Collection 10.1 in EPSG:4326 is the strongest default land-cover and change-detection layer, which fixes the realistic change-detection cadence at annual with roughly a one-year lag, any 10 m ambition must be flagged beta rather than promised, and as a heavy national raster it doubles as the tile-path and I6 memory-budget fixture.
- **INPE TerraBrasilis (deforestation: PRODES and DETER).** PRODES is the official annual native-vegetation-suppression polygon set (the audited clear-cut increment on a fixed yearly cycle); DETER is the near-real-time alert product (daily, an alert feed, not the official rate). Both now reach beyond Amazonia: PRODES covers Amazon, Legal Amazon, Cerrado, Caatinga, Mata Atlantica, Pampa, and Pantanal, and DETER publishes daily for the Amazon and Cerrado with experimental expansion to the Pantanal, confirmed against the live [WFS GetCapabilities](https://terrabrasilis.dpi.inpe.br/geoserver/ows?service=WFS&version=2.0.0&request=GetCapabilities). The native-vegetation-suppression data was refreshed in March 2026 under the BiomasBR program, so it is a live source. It arrives as **Shapefile** through the [download area](https://terrabrasilis.dpi.inpe.br/en/download-files/), and the [GeoServer OWS endpoint](https://terrabrasilis.dpi.inpe.br/geoserver/ows) additionally serves the same layers as **WFS, WMS, WCS, and CSW** in GeoJSON, KML, CSV, GML, and zipped Shapefile, which doubles as a real B3 (add-a-data-source) fixture, not just a file import. Native CRS is **SIRGAS 2000 geographic (EPSG:4674)**, declared as the layer DefaultSRS in the capabilities, license **CC-BY-SA 4.0**. **Microdecision:** PRODES and DETER are the authoritative deforestation reference layers and they are EPSG:4674-native, which makes SIRGAS 2000 a day-one reprojection target, and their two cadences map cleanly onto Mapsift's change-detection model as an annual audited tier (PRODES) and a near-real-time alert tier (DETER); the WFS-with-date-filter access path makes both incrementally syncable rather than a full re-download.
- **IBGE territorial meshes (malhas territoriais).** The official administrative-boundary geometries; the current edition is the **2024 Malha Municipal Digital** (5,573 municipality geocodes), with the full hierarchy of municipalities, immediate and intermediate geographic regions, states, regions, and country, plus the related biome, Brazilian Legal Amazon, and census-sector products in the same geosciences area. It ships as **Shapefile and GeoPackage**, native CRS **SIRGAS 2000 (EPSG:4674)**, public open government data, from the [malhas page](https://www.ibge.gov.br/geociencias/organizacao-do-territorio/malhas-territoriais/15774-malhas.html) and the [geosciences downloads portal](https://www.ibge.gov.br/geociencias/downloads-geociencias.html). It remains the right awkward-case fixture for two reasons confirmed in practice: the shapefiles historically carry **Latin-1 (ISO-8859-1) encoding** with accented municipality names, so a UTF-8 assumption mojibakes "São" and "Rondônia", and the 7-digit IBGE municipality geocode must be carried as a string, not an integer, or leading zeros are lost. **Microdecision:** the IBGE 2024 malhas in EPSG:4674 are the default administrative-boundary and spatial-join reference (the join key for any "which municipality, state, or biome does this feature fall in" query), and they reinforce SIRGAS 2000 (EPSG:4674) as the canonical national datum to standardize on, since IBGE, TerraBrasilis, CAR, and SIGEF all publish in it.
- **CAR (Cadastro Ambiental Rural, via SICAR).** The national environmental registry of rural properties (SICAR, under the Forest Code, Law 12,651/2012), and the legal-weight geometry par excellence. A CAR record is a self-declared geospatial dossier of one rural property: the property perimeter (área do imóvel) plus the internal environmental themes overlaid on it, namely the Permanent Preservation Area (APP), the Legal Reserve, native-vegetation remnant, consolidated-use area, restricted-use area, hydrography, and administrative easement. For OQ-8 this is the grounding case, and the verified anchor is not the polygon: legal weight keys off the pair **`cod_imovel`** (the structured CAR registration code, persistent and unique) and **the registration status `situacao_cadastro`** (Ativo, Pendente, Cancelado, Suspenso), layered over an analysis status, because a CAR is not legally settled merely by existing. It downloads as **Shapefile (and CSV)** per state and municipality, native CRS **EPSG:4674**, from the [SICAR portal](https://car.gov.br/) and the [public-consultation download portal](https://consultapublica.car.gov.br/publico/imoveis/index); access is **public but gated**, email plus captcha and deliberately rate-limited to discourage mass download (no published per-day number, bulk scraping is blocked by design). **Microdecision, and it was overruled where it went furthest (2026-07-31):** the identity half stands, legal weight keys off `cod_imovel` rather than off the geometry, which makes a CAR perimeter or reserve exactly the kind of feature where preserve-not-discard (C7) and the authored chain (C13) must hold. The **status half was rejected**: this note proposed requiring an Ativo `situacao_cadastro`, and PRD M7 settled the opposite, because a registration status is assigned on submission before any analysis, a record under challenge is when a boundary error is most expensive, and a protection that switches with a slowly-synchronised external state opens the window this product exists to close. The status is recorded and displayed as provenance and never arms or disarms the protection. This is the reference document behaving as designed: a Microdecision is evidence offered to a decision, never the decision; the exact `.dbf` column spellings were not pinnable against the captcha-gated official schema and should be confirmed against an actual downloaded file. **On area:** submission accepts SIRGAS 2000 geographic or UTM, and the analysis chain that produces the hectare figures (the MMA methodology and the CSR/UFMG CAR 2.0 note) reprojects the geometries to a **South America Albers equal-area conic on SIRGAS 2000** before computing property, APP, legal-reserve, and remnant areas. That is a different metric frame from the SGL the certified SIGEF parcel uses, on the same land, which is the concrete reason PRD M5 binds the frame to the purpose instead of fixing one globally. This one is a secondary source (the methodology notes, not a captcha-free primary norm) and is labelled as such.
- **SIGEF and INCRA (georeferenced parcels, the cadastral case).** SIGEF (Sistema de Gestão Fundiária) is INCRA's system that certifies the georeferenced limits of a rural property under Law 10,267/2001; the certified objects are the parcela (the certified boundary), its vertices (surveyed corners), and limites (boundary segments). The legal-weight anchor is the **certification code (número de certificação)** issued by INCRA, and the precision is not free-form: certified parcels must meet the NTGIR (the technical norm for georeferencing rural properties), whose historical headline is a 0.50 m positional accuracy on the boundary vertices, far tighter than CAR's self-declared sketch. This is the sharp distinction from CAR: SIGEF is a surveyed, INCRA-certified cadastral parcel with legal positional precision, where CAR is a self-declared environmental registry. It arrives as **Shapefile** (plus xlsx, CSV, XML), native CRS **SIRGAS 2000 (EPSG:4674)**, from the [SIGEF portal](https://sigef.incra.gov.br/) and the [Acervo Fundiário portal](https://acervofundiario.incra.gov.br/), free of charge but **requiring an authenticated gov.br account**, downloadable per state. **Microdecision:** OQ-8 should treat a SIGEF-certified parcel as the strongest legal-weight feature, outranking a CAR perimeter for the same land and keyed off the certification code; it is datum-aligned with the rest of the stack on EPSG:4674 but, unlike the public IBGE, MapBiomas, and TerraBrasilis layers, it sits behind a gov.br auth gate, which is a real ingestion-pipeline cost. **Confirmed against the norm (re-verified 2026-07-31, primary source `sigef.incra.gov.br/static/documentos/manual_geo_imoveis.pdf` and `.../portaria_629.pdf`), and the edition changed:** the 2026-07-30 entry here cited the **NTGIR 3rd edition (INCRA, 2013)**, which **Portaria INCRA 629 of 05/04/2022 revoked**, together with the Manual Técnico de Posicionamento 1st edition and the Manual Técnico de Limites e Confrontações 1st edition. The live standard is the **MTGIR 2nd edition**, approved by Portaria INCRA 2.502 of 22/12/2022 and published 23/12/2022. The content Mapsift depends on survived intact and renumbered: item **1.4.4** fixes the positional precision of limit vertices at **better than or equal to 0,50 m on artificial limits, 3,00 m on natural limits, and 7,50 m on inaccessible limits** (so the widely quoted 0,50 m headline is the artificial-limit case rather than a blanket figure), plus a tolerance of at most three times that value between two credentialed surveyors on the same vertex; item **1.4.6** rules that **"O cálculo de área deve ser realizado com base nas coordenadas referenciadas ao Sistema Geodésico Local (SGL)"** and cross-refers to item **3.8.1** for the geocentric-to-local conversion; item **3.8.1(a)** fixes the **origin of the local frame, for the purpose of computing area, as the mean of the coordinates of the parcel in question**, which settles the ambiguity PRD M5 had left open between a chosen vertex and the parcel centroid; item **3.8.3** fixes the computation as the Gauss formula over the local cartesian coordinates expressed in hectares, and states in the norm's own words that the local-frame result "expressa melhor a realidade física" than the UTM value "que era adotado anteriormente", with the distortion growing with the parcel's surface; and item **3.8.5** fixes the azimuth by the inverse geodetic problem after Puissant, in sexagesimal. That last one is load-bearing for Mapsift and is why PRD M5 makes the metric frame a per-purpose choice: the legal area of a certified parcel is a local-topocentric-plane figure, not a UTM figure and not a geodesic-on-the-ellipsoid figure.

The load-bearing pattern across these five: four of them (IBGE malhas, TerraBrasilis PRODES and DETER, CAR, SIGEF) are natively SIRGAS 2000 (EPSG:4674), and only MapBiomas is EPSG:4326, which makes EPSG:4674 the non-negotiable day-one reprojection target, with EPSG:4326 second and the SIRGAS 2000 UTM zones (18S to 25S over Brazil) third. And legal weight, the OQ-8 question, keys off registry identity-and-status fields rather than geometry, with SIGEF's certification code outranking CAR's `cod_imovel` in precision.

### 1.3 Format and CRS fixtures (you need one exemplar of each, not real data)

- **Natural Earth.** The canonical free test vector, worldwide, at three scales (1:10m most detailed, 1:50m medium, 1:110m schematic), split into cultural (countries, states, populated places, roads) and physical (coastline, land, ocean, rivers, lakes) themes, though not every layer exists at all three scales. Formats are ESRI Shapefile plus GeoPackage, SQLite, GeoJSON, KML, and FlatGeobuf; native CRS WGS84 (EPSG:4326); raster as TIFF with a TFW world file. It is **public domain**, explicitly free for commercial and non-commercial use with no attribution required, maintained under NACIS and hosted on AWS. Root: [naturalearthdata.com](https://www.naturalearthdata.com/). Use it as the baseline WGS84 vector fixture across geometry types, and note the licensing point for later: it is the always-safe small-scale overview layer a commercial product can ship with zero license friction, the counterpoint to GADM in section 1.4, which cannot.
- **GeoParquet and FlatGeobuf samples.** The GeoParquet project and the FlatGeobuf project publish example datasets in their repositories and docs; use them as the modern-columnar and the streaming-binary format fixtures, the ones GDAL must handle that older web-GIS tooling often does not.
- **The deliberately broken fixtures.** A Shapefile zip missing its `.shx` or `.dbf` (the validation-error case), a file with no `.prj` (the assumed-CRS case), and a file in SIRGAS2000 UTM (the reprojection-correctness case). These are the fixtures that prove B2's acceptance criteria, not the happy-path ones.

### 1.4 General-purpose and regional sources (the product is general-purpose; Brazil is the anchor, not the ceiling)

Mapsift is a general-purpose tool with a Brazilian anchor, so the test corpus must prove import and analysis on foreign data too, otherwise it only validates half of what the product promises. These are the sources the general-purpose GIS tools actually consume, by region. Each one also widens the CRS axis beyond SIRGAS2000, which matters because a general-purpose tool reprojects every national grid, not only Brazil's.

Global, region-agnostic, the baseline corpus:

- **OpenStreetMap via Geofabrik.** [Daily regional extracts](https://download.geofabrik.de/) of the full OSM database sliced by continent, country, and subnational region: roads and paths, buildings, waterways and water bodies, land use and land cover, points of interest, administrative boundaries, and railways, with completeness that varies sharply by region (dense in Europe, patchier in rural Brazil). Geofabrik is the single best source for the **`.osm.pbf`** fixture and for mid-size real vector in any country, also serving a thematically pre-split ESRI Shapefile per region; the [HOT Export Tool](https://export.hotosm.org/) adds GeoPackage, KML, GeoJSON, and MBTiles on demand. Native CRS WGS84 (EPSG:4326), license **ODbL 1.0**. **Microdecision:** ODbL is share-alike, so a derivative database Mapsift builds from OSM and then publicly redistributes inherits ODbL and the "© OpenStreetMap contributors" attribution; it does not infect Mapsift's own user-drawn elements or application code, and producing maps and analysis from it is fine with attribution, but redistributing an enriched OSM dataset triggers share-alike. OSM is safe as a basemap and reference import; it is the share-alike clause that pushes a commercial product toward Overture for any base data it intends to redistribute.
- **Overture Maps Foundation.** The Linux-Foundation-backed open base-map project that re-packages OSM plus corporate-contributed open data into a clean, conflated, cloud-native schema, a genuinely useful newer source. The current schema organizes data into six themes: [buildings](https://docs.overturemaps.org/guides/buildings/) (footprints with height where known), [transportation](https://docs.overturemaps.org/guides/transportation/) (a segment-and-connector road graph), [places](https://docs.overturemaps.org/guides/places/) (POIs with categories), base (land, water, land use and cover, infrastructure), divisions (administrative boundaries and named places), and addresses, with a stable GERS ID on every feature for cross-release joins. It is distributed as [GeoParquet](https://docs.overturemaps.org/getting-data/) from AWS S3 (us-west-2) and Azure, with a STAC catalog, the `overturemaps` Python CLI, and a no-auth browser [Explorer](https://explore.overturemaps.org/); native CRS is OGC:CRS84 (longitude-latitude WGS84, equivalent to EPSG:4326); releases are [monthly since October 2023](https://docs.overturemaps.org/release-calendar/), with mid-2026 releases on the `2026-06-17.0` pattern. The license is the crux and it is split per theme, verified on the [attribution page](https://docs.overturemaps.org/attribution/): **places is CDLA Permissive 2.0** (no share-alike), while buildings, transportation, base, and divisions are **ODbL** because they derive from OSM, and addresses is mixed. **Microdecision:** Overture earns the default base-layer slot, but the "permissive" story is only fully true for the **places** theme, which is the commercially-clean POI layer where Overture decisively beats raw OSM; the other themes carry the same ODbL obligation as OSM, so adopting them buys cleaner pre-conflated GeoParquet packaging, not an escape from share-alike. Ship Overture places as the POI base, use its buildings, transportation, and divisions as a ready-to-tile alternative to assembling them from OSM yourself, and keep Geofabrik as the raw-import and freshness fallback.
- **GADM and Natural Earth for administrative boundaries.** GADM gives high-resolution national, state, and municipal boundaries worldwide (the global equivalent of the IBGE meshes, far finer than Natural Earth); the [current version is 4.1](https://gadm.org/data.html) with version 5 announced for early 2026 (confirm the live version string at integration time), in GeoPackage, Shapefile, GeoJSON, and KMZ, native CRS EPSG:4326. The license is the catch and it is hard: GADM is [free for academic and non-commercial use only, with redistribution or commercial use not allowed without prior permission](https://gadm.org/license.html). **Microdecision:** GADM is effectively off-limits as a shipped layer in a commercial product, so do not bundle it; use sovereign sources (IBGE for the Brazilian anchor, national agencies elsewhere) or Overture's divisions theme (ODbL, commercially usable with share-alike) for shippable admin boundaries, and keep GADM only as a research convenience. Natural Earth (already in 1.3, public domain) is the always-safe small-scale baseline that GADM cannot be.
- **ESA WorldCover.** Global land cover at 10 m from Sentinel-1 and Sentinel-2, with 11 classes (tree cover, shrubland, grassland, cropland, built-up, bare or sparse vegetation, snow and ice, permanent water, herbaceous wetland, mangroves, moss and lichen), the global counterpart to MapBiomas, CORINE, and NLCD. Verified status as of mid-2026: only **two versions exist, v100 (2020) and v200 (2021)**, with no 2022-or-later release, distributed as [Cloud-Optimized GeoTIFF in 3x3 degree tiles](https://esa-worldcover.org/en/data-access), native CRS EPSG:4326, license **CC-BY 4.0** (commercially usable with attribution), from the [viewer](https://esa-worldcover.org/en), the [AWS Open Data bucket](https://registry.opendata.aws/esa-worldcover-vito/), Zenodo, and Earth Engine. **Microdecision:** WorldCover is the default global land-cover reference layer and a commercially safe packaged classification, but the two-epoch limit means it is a baseline fixture, not a change-detection cadence source; Sentinel-2 itself is the cadence engine.
- **Copernicus DEM (GLO-30 and GLO-90).** The global elevation terrain fixture, a Digital Surface Model (it includes buildings and vegetation, not bare earth) from the TanDEM-X mission, GLO-30 at roughly 30 m and GLO-90 at 90 m, the source for hillshade, slope, aspect, viewshed, and profiles. Format is [Cloud-Optimized GeoTIFF](https://registry.opendata.aws/copernicus-dem/), horizontal CRS EPSG:4326 with the vertical reference EGM2008 (geoid heights), now **free and open** for both resolutions, reachable via the [AWS Open Data Registry](https://registry.opendata.aws/copernicus-dem/) (public S3, no-sign-request, no account), the [Copernicus Data Space](https://dataspace.copernicus.eu/), and [OpenTopography](https://portal.opentopography.org/raster?opentopoID=OTSDEM.032021.4326.3). **Microdecision:** the default global terrain layer for derived analyses; the no-sign-request COG path is the cheapest integration, GLO-30 for analysis and GLO-90 as the lighter fallback. It is a static 2021-release product (no active versioning), which is fine for terrain, and ocean tiles are absent.
- **Sentinel-2 via the Copernicus Data Space Ecosystem (CDSE).** The same free imagery that is Mapsift's intended default basemap source; a scene pulled directly is the raster and COG fixture and exercises the STAC path of B3. The instrument is 13 bands at three resolutions (10 m for blue, green, red, NIR; 20 m for red-edge and SWIR; 60 m atmospheric), in L1C (top-of-atmosphere) and L2A (atmospherically corrected surface reflectance, analysis-ready), with a **5-day revisit** (2 to 3 days at mid-latitudes), which makes Sentinel-2 the real change-detection cadence engine unlike WorldCover's two static epochs. Native CRS is **UTM and WGS84** (tiled per UTM zone, so Brazilian imagery lands in zones 18S to 25S and is reprojected to a common display CRS); formats are SAFE (JPEG2000 internally) and derived COGs. The old SciHub is retired; access is the [Copernicus Data Space Ecosystem](https://dataspace.copernicus.eu/) via its [STAC API](https://documentation.dataspace.copernicus.eu/APIs/STAC.html), S3 (the `eodata` store), the Sentinel Hub APIs, and the [openEO API](https://dataspace.copernicus.eu/ecosystem/services/openeo); the data is free, full, and open. **Microdecision:** Sentinel-2 via CDSE is the right default imagery source, but the cost reality (section 1.5) forces a split: offer unlimited viewing of pre-tiled imagery served from Mapsift's own storage, and meter the heavy spectral processing (on-the-fly NDVI, cloud-masked composites, openEO jobs) per tenant, because that processing maps directly onto CDSE's metered Processing Units and credits.
- **STAC catalogs beyond Sentinel: AWS Earth Search and Microsoft Planetary Computer.** Two independent STAC backends that prove the B3 STAC data-source provider is not single-vendor. [AWS Earth Search](https://earth-search.aws.element84.com/v1) (Element 84, over AWS Open Data) exposes Sentinel-2 L1C and L2A and Collection-1 L2A, Landsat Collection 2, Sentinel-1 GRD, NAIP, and the Copernicus DEMs as COGs from us-west-2; the [Microsoft Planetary Computer](https://planetarycomputer.microsoft.com/) serves a curated catalog of more than a hundred datasets (Sentinel, Landsat, NAIP, MODIS, ESA WorldCover, Copernicus DEM, and more) on Azure. Both are STAC 1.0, so one Mapsift STAC client hits either; assets are COG with per-item CRS in the STAC `proj` extension (Sentinel-2 native UTM) and metadata in EPSG:4326. The access and cost reality is the caveat: Earth Search is free and anonymous to query, but some underlying buckets are **requester-pays** (`s3://` URLs need AWS credentials and the egress falls on the reader), and the Planetary Computer is anonymously accessible but requires a free SAS token to sign asset URLs and [rate-limits egress](https://planetarycomputer.microsoft.com/docs/concepts/sas/). Verified mid-2026 status: the Planetary Computer is **still operating**; only the interactive compute Hub was retired in 2024, and [Planetary Computer Pro](https://azure.microsoft.com/en-us/products/planetary-computer-pro) is a separate paid Azure product, not a replacement for the free public API. **Microdecision:** document both as the evidence that B3 is multi-vendor and as alternate imagery backends with a real vendor-failover story, while carrying the honest caveat that neither is free at scale (requester-pays egress on AWS, rate-limited egress and a 2026 signal of optional paid support on Azure).
- **Global Forest Watch and the Hansen Global Forest Change.** The global tree-cover-change baseline and the global counterpart to PRODES and DETER. The [Hansen et al. (UMD) Global Forest Change](https://developers.google.com/earth-engine/datasets/catalog/UMD_hansen_global_forest_change_2025_v1_13) product, verified latest **v1.13 covering 2000 to 2025**, carries a `treecover2000` canopy-percentage baseline, an annual `lossyear`, a `loss` mask, and a cumulative `gain` layer, at roughly 30 m, as GeoTIFF 10x10 degree granules in EPSG:4326, license **CC-BY 4.0**; separately, [GFW's integrated alerts](https://www.globalforestwatch.org/blog/data-and-tools/integrated-deforestation-alerts/) combine the GLAD-L, GLAD-S2, RADD, and DIST-ALERT near-real-time systems. **Microdecision:** at global scope the annual Hansen layers anchor the baseline and historical change-detection workflow (yearly cadence) while the GFW alerts give the near-real-time tier (days), the same two-tier split as PRODES and DETER but worldwide, and the permissive CC-BY license means a shipped feature can lean on it, unlike WDPA below.
- **WDPA / WDPCA, the World Database on Protected Areas (Protected Planet).** The global protected-areas and OECM database, now branded WDPCA, the most domain-relevant of the candidate sources because a global protected-areas layer maps straight onto the preservation-area domain. The [March 2026 release](https://www.protectedplanet.net/en/thematic-areas/wdpa) holds over 312,000 protected areas and more than 7,000 OECMs as polygons and points with designation, IUCN management category, status, and governance attributes, as Shapefile and File Geodatabase, monthly, native CRS EPSG:4326. The license is the blocker and it is hard, verified on the [UNEP-WCMC WDPA license](https://www.unep-wcmc.org/en/wdpa-data-license): no commercial use without prior written permission, and a no-redistribution clause that explicitly forbids serving the data through a web service or interactive web map, which is exactly the mechanism Mapsift would use for an overlay. **Microdecision:** catalog WDPA as the canonical global protected-areas reference, but flag it license-gated and not shippable as a default overlay; the realistic shapes are a bring-your-own overlay where the user accepts Protected Planet's terms and the data never transits Mapsift's redistribution surface, or a negotiated commercial license with UNEP-WCMC before any hosted preservation-area feature leans on it.

Europe:

- **Copernicus Land Monitoring Service, CORINE Land Cover and CLC+ Backbone.** Classic CORINE is the pan-European land-cover inventory, 44 thematic classes, at the reference years 1990, 2000, 2006, 2012, and 2018, each paired with a change (CHA) layer, on a six-year rhythm with a 25 ha minimum mapping unit (5 ha on the change layers). Verified mid-2026: the classic series is alive, a CLC 2024 reference year is in production for the 35th anniversary (11 countries, not yet finalized, so 2018 remains the newest finalized classic epoch), and the newer [CLC+ Backbone](https://land.copernicus.eu/en/products/clc-backbone) supplements rather than supersedes it, a 10 m raster with a coarse 11-class legend on a biennial cadence. The two are not interchangeable: classic CORINE gives the rich 44-class legend and clean six-yearly change pairs, CLC+ gives finer resolution but a thin legend. Both are distributed in **ETRS89 / LAEA (EPSG:3035)**, classic CORINE as vector polygon topology plus a derived 100 m GeoTIFF, under the [free, full, and open Copernicus data policy](https://land.copernicus.eu/en/products/corine-land-cover) (attribution, no implied EU endorsement), though the current CLMS portal requires EU Login registration to download and the in-browser clip is size-capped (bulk pulls go through the M2M API). **Microdecision:** EPSG:3035 is an equal-area azimuthal projection on a European datum, structurally unlike anything Brazil uses, so it is the key non-SIRGAS, non-UTM reprojection test and a day-one target; classic CORINE is the European change-detection fixture, CLC+ the 10 m supplement, and the corpus loader must handle an EU-Login-gated portal rather than an anonymous download.

North America (United States):

- **USGS National Land Cover Database (NLCD) and Annual NLCD.** The definitive US 30 m land cover, and as of mid-2026 the line has split. The [legacy NLCD](https://www.usgs.gov/centers/eros/science/national-land-cover-database) is the epoch-based series (2001 to 2021, the 16-class land cover plus impervious surface and tree canopy); the headline move is [Annual NLCD](https://www.mrlc.gov/data/project/annual-nlcd), Collection 1.1, published June 2025, extending a true annual record to **1985 through 2024** with six science products (land cover, land-cover change, confidence, fractional impervious surface, impervious descriptor, spectral change day-of-year), CONUS-only so far. Format is GeoTIFF (Annual NLCD as COG) at 30 m; the native grid is **Albers Equal Area Conic**, and there is a verified subtlety: Annual NLCD uses Albers on the **WGS84 datum** while legacy NLCD used Albers on **NAD83**, so an importer that assumes NAD83 is subtly wrong on Annual NLCD and must read the datum from the file. License is US-government public domain, via the [MRLC viewer](https://www.mrlc.gov/viewer/), EarthExplorer, ScienceBase, and AWS S3 in us-west-2. **Microdecision:** Albers Equal Area Conic is a second mandatory day-one foreign-grid target (read the datum, do not assume it), and Annual NLCD's genuinely annual 1985 to 2024 record is a harder change-detection cadence fixture than any epoch-based product, the prime US analogue to MapBiomas.
- **USGS The National Map (TNM).** The US one-stop equivalent of the IBGE-plus-INPE pairing: elevation (3DEP lidar and DEM), hydrography (the legacy NHD and the newer 3DHP), federal-land and administrative boundaries, transportation, structures, GNIS names, NAIP orthoimagery, and NLCD-derived land cover, via the [TNM Download client](https://apps.nationalmap.gov/downloader/) and the TNMAccess API, all public domain. The CRS story is deliberately heterogeneous and that is the point: the 3DEP DEMs are unprojected geographic decimal degrees on NAD83 at 1/3, 1, and 2 arc-seconds, while the 1 m DEMs are projected per UTM zone (NAD83 horizontal, NAVD88 vertical), so a single download path exercises NAD83 geographic and multiple NAD83 UTM zones at once, with State Plane a known US grid to support on the same path. **Microdecision:** TNM proves Mapsift must reproject NAD83 geographic, NAD83 UTM zones, and State Plane on the import path, and it is the right foreign multi-theme fixture (elevation plus hydrography plus boundaries) for non-SIRGAS data that is not a single uniform grid; the 3DEP web services restrict their CRS options to CRS:84, EPSG:4326, and EPSG:3857, so the richer grid variety lives in the downloadable files.
- **US Census TIGER/Line.** The US counterpart to the IBGE meshes: the full hierarchy of legal and statistical boundaries (states, counties, census tracts, block groups, places, road edges, and hydrography), carrying geographic codes for joining to demographic data but no demographic data themselves; the latest vintage is the 2025 TIGER/Line, released September 2025. Formats are Shapefile and File Geodatabase; native CRS is **NAD83 geographic (EPSG:4269)**, the simplest foreign-grid case, geographic not projected; license is public domain ([CC0 on data.gov](https://catalog.data.gov/dataset/tiger-line-shapefile-current-nation-u-s-state-and-equivalent-entities)), via the [TIGER access page](https://www.census.gov/geographies/mapping-files/time-series/geo/tiger-line-file.html). **Microdecision:** EPSG:4269 (NAD83 geographic) is a required day-one reprojection target and the easiest foreign case, and TIGER/Line is the administrative-mesh fixture that confirms Mapsift imports a foreign boundary hierarchy the way it imports IBGE meshes.

Catalogs to find more without re-searching: the awesome-geospatial-data-sources list ([github.com/iamtekson/awesome-geospatial-data-sources](https://github.com/iamtekson/awesome-geospatial-data-sources)) aggregates global open sources by theme and format, and Google Earth Engine's catalog is the broadest single index when a programmatic pull is acceptable (free for noncommercial and research use; commercial use requires a paid plan, see section 1.5).

The national grids these foreign sources establish, each a distinct non-SIRGAS reprojection test, are the day-one set beyond Brazil's: EPSG:3035 (ETRS89 / LAEA, equal-area azimuthal) from CORINE, Albers Equal Area Conic (with the NAD83-versus-WGS84 datum split) from NLCD, NAD83 geographic and NAD83 UTM zones (plus State Plane) from TNM, and EPSG:4269 (NAD83 geographic) from TIGER/Line. Together with SIRGAS 2000 (EPSG:4674) and its UTM zones from section 1.2, that is the reprojection surface the import path must land on day one.

### 1.5 Serving-cost reality (the data is free, serving it is not)

A recurring product microdecision sits underneath every "unlimited" imagery or heavy-raster feature: the data above is mostly free to obtain, but serving it to users is not, and the cost lives in processing and egress, not storage. The figures below were verified against live pricing and quota pages in mid-2026; pricing moves, so each is dated and linked, and any number quoted should be re-confirmed against the live page before it enters a real cost model.

- **Copernicus Data Space processing economics.** CDSE is free for browse and bounded access, but the free tier is metered tightly enough that "unlimited Sentinel-2" cannot ride on live CDSE calls. Per the [quotas documentation](https://documentation.dataspace.copernicus.eu/Quotas.html), each free user gets 10,000 Sentinel Hub Processing Units per month (capped at 300 per minute) and 10,000 openEO credits per month, plus 50,000 Sentinel Hub and 10,000 OData/STAC requests and a 12 TB rolling-30-day download cap; past quota you are throttled, and large-scale or commercial use is pushed off-platform to CREODIAS (no clean public per-unit commercial rate to model from a single page). A Processing Unit scales with output size, number of images, bands, and format. The consequence for Mapsift: pull Sentinel-2 once into Mapsift's own storage as COGs and serve from its own tiling stack, rather than proxying live PU-billed Sentinel Hub requests, and treat CDSE and openEO as a batch-ingestion and heavy-analysis backend within the free quota, not a real-time tile source.
- **Object-storage egress, not storage, is the dominant cost.** As of mid-2026 AWS S3 charges roughly $0.09/GB egress to the internet for the first tier, dropping with volume, per the [S3 pricing page](https://aws.amazon.com/s3/pricing/); a tile-serving GIS is egress-dominated, so that line item is what makes "unlimited" hard to model, and Requester Pays only helps when someone else is the reader, not when the product serves its own users. The lever is the zero-egress providers: [Cloudflare R2](https://developers.cloudflare.com/r2/pricing/) charges $0 egress (storage around $0.015/GB-month), and Backblaze B2 is free egress when fronted by Cloudflare. The [AWS Open Data Sponsorship Program](https://registry.opendata.aws/) sponsors storage and egress for the canonical public buckets (the Sentinel-2 L2A COGs in `sentinel-cogs`, us-west-2, are readable unauthenticated and free), but only for reading the sponsored bucket in place; copying into your own bucket or reading cross-region pays normal egress. **Decision shape:** store and serve Mapsift's own tiles on a zero-egress provider (R2, or B2 behind Cloudflare), read sponsored Sentinel-2 COGs in place in us-west-2, and reserve S3 or MinIO for the parts that genuinely need them.
- **Dynamic tiling versus pre-generated.** [TiTiler](https://developmentseed.org/titiler/) (a rasterio and rio-tiler FastAPI app) is compute-on-read: every tile is a GDAL range-read plus rescale and encode on CPU, so cost scales with request volume. [PMTiles](https://docs.protomaps.com/pmtiles/) is the opposite, a single cloud-optimized archive served directly off static storage by HTTP range requests with no tile server at all, so on a zero-egress provider it serves at near-zero marginal cost. **Decision shape, the same gate the foundation already states for pre-generated tiles:** keep dynamic TiTiler for genuinely dynamic raster (band math, NDVI rescale, user-chosen stretch) where pre-rendering every variant is infeasible, and switch a layer to pre-generated PMTiles the moment it is stable, hot, and read-heavy, which for a default basemap-style layer is almost immediately.
- **Google Earth Engine and Planetary Computer are not free commercial backends.** Google Earth Engine is free only for noncommercial, research, and news use; commercial use requires a paid plan with a platform fee plus per-EECU compute, so leaning on it means modeling EECU cost per operation (the same "serving is not free" wall as CDSE Processing Units). The Microsoft Planetary Computer's free hosted-compute Hub was retired in 2024; its open STAC catalog stays free as a discovery index, but hosted workflows now mean the paid Planetary Computer Pro on Azure. **Decision shape:** use these only as free open-data discovery layers, pull the actual pixels from free open-data buckets, and own the serving stack so the product's cost is Mapsift's to model rather than a third party's metered compute on every user action.

## Part 2. Tool use and expected behavior (the level-two reference)

### 2.1 How to read this part

Most of the native analysis tools are wrappers over two libraries, GDAL and GEOS, plus the QGIS Processing framework, and Mapsift runs the authoritative result in PostGIS server-side. So the canonical behavior of a tool is documented in three places, and the per-tool table below points to them:

- **QGIS Processing algorithms documentation** is the dictionary of "what this tool does," with diagrams and the use described per algorithm. Root: [docs.qgis.org/latest/en/docs/user_manual/processing_algs](https://docs.qgis.org/latest/en/docs/user_manual/processing_algs/) (the QGIS provider sections cover vector overlay, vector geometry, vector analysis, raster analysis; the GDAL provider covers conversion and projection).
- **PostGIS reference** is the exact behavior of the function Mapsift actually calls server-side, including edge cases. Root: [postgis.net/docs/reference.html](https://postgis.net/docs/reference.html).
- **The CRS rule, which is the level-two acceptance for nearly every tool.** Processing always runs in the input layer's CRS, and a CRS mismatch silently produces an empty or wrong result (two layers that look like they overlap may not, in their native coordinates). Distance and area are never computed in degrees on a geographic CRS, or the figure is wrong while the tool still "succeeds." This is the single most common failure that passes a level-one smoke test and fails level two, and it is exactly what Mapsift's authoritative-metric and SIRGAS 2000 rules exist to prevent. **Which metric frame replaces the degrees is not one answer, and PRD M5 is the authority, not this paragraph:** the frame is chosen by the metric's purpose, geodesic on the SIRGAS 2000 ellipsoid for a generic or preview figure, the Sistema Geodésico Local for the area of a certified rural parcel (MTGIR 2nd edition items 1.4.6 and 3.8.3, section 1.2 above), and an equal-area conic for the CAR and environmental area chain. UTM is fine for a local buffer distance and is not where a legal area is produced.

### 2.2 Proximity (what is near what)

- **Buffer** (PostGIS `ST_Buffer`, QGIS Buffer). Produces a zone covering all points within a distance of a feature. Use case, and the anchor case for Mapsift: a Permanent Preservation Area (APP) is legally a buffer of a fixed width around hydrography, so buffer is not a generic tool here, it is the operational definition of an APP. Typical professional: the environmental analyst delimiting APPs. Level-two acceptance: distance is in the SRS units, so on a projected CRS (UTM) a 100 m buffer is 100 m; on EPSG:4326 the same "100" is degrees and is wrong. Test on a UTM fixture and confirm the resulting area is plausible.
- **Distance and within-distance** (PostGIS `ST_Distance`, `ST_DWithin`). "How far," and "what is within X of this." Use case: impact proximity, "which parcels are within 500 m of the clearing." Acceptance: same CRS-units rule; `ST_DWithin` on geography is meters, on geometry is SRS units.

### 2.3 Overlay (what coincides in space, the bulk of environmental work)

- **Intersect** (PostGIS `ST_Intersection` for geometry, `ST_Intersects` for the boolean; QGIS Intersection). Keeps the overlapping portion, output carries attributes from both layers. Use case: "did the clearing invade the reserve," the daily question. Acceptance: two non-touching layers return empty, not error; a CRS mismatch returns a spurious empty, so the inputs must share a CRS first.
- **Difference / Subtract** (PostGIS `ST_Difference`, QGIS Difference). Keeps the part of A outside B. Use case: "which part of the property is outside the APP and may be used." Acceptance: a feature fully inside B yields empty; partial overlap is split along B's boundary.
- **Clip** (QGIS Clip; PostGIS via `ST_Intersection`). Same geometry as intersect but used to cut to an area of interest, the "cookie cutter," typically run before a heavy operation to reduce data. Acceptance: features outside the clip extent are dropped, features straddling it are split.
- **Union** (PostGIS `ST_Union`, QGIS Union). Combines features. Note the documented gotcha: overlaps within a single input are not resolved by one pass, you union the result again. Use case: merge fragments into one area to measure total.
- **Dissolve** (QGIS Dissolve; PostGIS `ST_Union` grouped by attribute). Merges features sharing an attribute into one. Use case: "fuse all forest fragments of the same class into one polygon to measure total area."
- **Symmetric difference** (PostGIS `ST_SymDifference`, QGIS Symmetrical difference). Keeps what is in one layer or the other but not both.

### 2.4 Aggregation and zonal statistics (how much of X inside each Y)

- **Count points in polygon** (QGIS Count points in polygon). Counts occurrences per region as an attribute. Use case: count of alerts per property.
- **Zonal statistics** (QGIS Zonal statistics; PostGIS raster `ST_SummaryStats`, `ST_Clip`). Raster summarized over vector zones. Use case, and one of the most-used environmental operations after buffer: "the mean NDVI inside each property," which collapses a heavy raster into one number per area. Acceptance: the statistic respects the nodata value and the zone geometry; the raster and vector must be in a compatible CRS.

### 2.5 Geometry and shape

- **Centroid** (PostGIS `ST_Centroid`, QGIS Centroids). Central point of a line or polygon. Use case: labeling, simplification.
- **Convex hull** (PostGIS `ST_ConvexHull`, QGIS Convex hull). Smallest polygon enclosing a set. Use case: "the area of occurrence of a species from its sighting points."
- **Voronoi** (QGIS Voronoi polygons). Divides space into zones of influence around points. Use case: "which collection station is nearest to each location." Rare in environmental work, which is why the PRD marks it extension, not native; listed here so the use is on record.

### 2.6 Raster and spectral

- **NDVI and band algebra** (raster calculator; the index is `(NIR - RED) / (NIR + RED)`). A closed formula, so it is a pure testable function: given known band values, the output is deductible and exact, the easiest level-two test in the whole set. Use case: vegetation cover and vigor, the domain core. Acceptance: a hand-computed pixel matches the tool's output for that pixel.
- **Reclassify, hillshade, slope, aspect** (QGIS raster analysis and terrain analysis; GDAL). Use cases: turning continuous values into classes, terrain visualization and derivation. Acceptance: deterministic given the input raster and parameters.

### 2.7 The level-two checklist a developer applies per tool

1. Did it run and return a geometry or value (level one).
2. Is the result in a projected CRS when the figure is a distance or area, never degrees on EPSG:4326.
3. Do the inputs share a CRS, so an empty result means genuinely no overlap and not a silent reprojection miss.
4. Does the documented edge case hold (non-touching inputs return empty not error; a feature inside the difference layer yields empty; nodata is respected in zonal stats).
5. For closed-formula tools (NDVI), does a hand-computed value match.

Levels three and up (does this match the biome, is the analysis methodologically right) are the engineer's, and feed OQ-5 and OQ-8, not this checklist.
